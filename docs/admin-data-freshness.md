# Актуальность данных админки TakeRide

Реализация от 20 сентября 2026 года. Основные списки остаются серверными; изменения передаются как сигналы перечитать соответствующие данные, без персональных данных в SSE.

## Обновление

- `AdminDataSync` существует только в административной оболочке для сотрудников.
- `/api/admin/events` защищён ролью. Передаёт темы `fleet`, `rides`, `users`, `feedback`, `parkings`, `map`, `service`, `support`.
- Изменения HTTP публикуются после успешного ответа записывающего обработчика. Архивирование парковки с HTTP 409 учтено отдельно; подтверждения прочтения чата исключены, чтобы не создавать цикл запросов.
- OMNI и внутренние события флота сбрасывают версию кеша до уведомления клиентов. Обычная телеметрия не обновляет тяжёлые пользовательские и аналитические агрегаты.
- Начальное SSE-событие перечитывает данные после подключения/переподключения. Heartbeat проверяет действительность сессии и роль каждые 25 секунд; клиент перезапускает зависшее соединение после 75 секунд без сигналов, проверяя его раз в 20 секунд.
- Резервный опрос касается только активных запросов открытой админки: операционные данные примерно раз в 20 секунд, аналитика не чаще раза в 60 секунд без событий. Возврат в видимую вкладку, фокус и восстановление сети запускают повторное чтение.
- Это не SLA: скрытая вкладка, длительные запросы и ограничения браузера могут увеличить задержку.
- Событийная шина локальна процессу. При нескольких backend-процессах или отдельном OMNI-процессе изменения другого процесса подхватывает резервный опрос; для мгновенной межпроцессной доставки нужен общий pub/sub.
- Обычный клиентский кеш приложения райдера не переведён на частый глобальный опрос. Общая подписка `/api/bikes/stream` использует один экземпляр EventSource на вкладку.

## Полнота данных

- `/api/admin/rides/page`, `/api/admin/users/page`, `/api/admin/feedback/page`: фильтры и поиск применяются на сервере, возвращаются `items`, `total` и необходимые счётчики/категории. Размер страницы UI: 50; API: до 200.
- Поиск буквальный: `%`, `_` и обратная косая черта экранируются. Значения передаются в SQL параметрами.
- Активные поездки для карты запрашиваются через `/api/admin/rides/active` независимо от исторического лимита.
- Отзывы о поездках и поддержке объединяются до сортировки и пагинации. Старый массивный `/api/admin/feedback` использует тот же SQL и `X-Total-Count`.
- Счётчик поездок за день использует агрегат БД, а не первые 100 поездок.
- CSV пользователей загружает страницы до конца; список исполнителей запрашивает сотрудников отдельно от первых 5000 пользователей.
- Пагинация имеет стабильное дополнительное упорядочивание по ID. Offset-пагинация не является транзакционным снимком всей выгрузки: вставки/удаления между запросами страниц могут сдвигать границы.
- `from=0` корректно означает всю историю. Относительные периоды пересчитываются при смене дня; таймер длительности активных поездок работает локально раз в секунду.

## Ошибки и восстановление

- Общая строка состояния показывает состояние канала, ошибки, время последнего успешного чтения и ручное обновление.
- До получения алармов сервером не показывается зелёный статус «Всё под контролем».
- Ошибки сервисных заявок, поддержки, чатов и слоёв карты обозначаются отдельно от пустого результата.
- Открытый чат перечитывается после переподключения и опрашивается резервно. Детали сервисной заявки имеют дочерний ключ кеша.
- Архивирование парковки отличено от сетевого отказа; оба списка парковок обновляются.

## Проверки

- Полный набор: 1169 тестов в 99 файлах, TypeScript и production-сборка.
- SSE проверен реальным HTTP-тестом: запрет анонимного/райдерского доступа, две независимые сессии, доставка изменения, восстановление после переподключения, снятие слушателей.
- Контролируемые тесты настоящего QueryClient проверяют повторную загрузку устаревших данных, область резервного опроса и зависимые ключи.
- Изолированный PostgreSQL: 5002 пользователя, 601 поездка, 1200 отзывов. Проверены старый активный заезд, поиск вне прежних лимитов, отсутствие повторов/пропусков на неизменяемых страницах, объединение отзывов, фильтры, счётчики и параметризация.
- В production-тестовом job добавлен PostgreSQL 16 и запуск `script/check-admin-data.ts`. Скрипт отказывается использовать базу вне локального `takeride_admin_test`; фикстуры никогда не создаются в production.

Локальный запуск интеграционной проверки:

```sh
ADMIN_DATA_TEST_DATABASE_URL='postgresql:///takeride_admin_test?host=/var/run/postgresql' npx tsx script/check-admin-data.ts
```

Реальные пользовательские поездки, платежи и аппаратные команды замкам не создаются этими тестами. Проверка живых production-сессий с настоящим замком остаётся отдельным эксплуатационным сценарием.
