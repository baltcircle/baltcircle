# Runbook: инциденты и топология (HIGH #23)

## Текущая топология (осознанное решение, 2026-08-18)

Прод — одна VM в Yandex Cloud:
- nginx (TLS-терминация, reverse proxy) + Docker (приложение) на одном хосте
- Приложение — один контейнер `baltcircle-mvp`, `restart: unless-stopped`
- БД — managed PostgreSQL в Yandex Cloud (резервирование и бэкапы уже на стороне провайдера, вне зоны риска этого документа)
- Загруженные файлы поддержки (`/home/yc-user/uploads`) — bind mount на диске этой же VM, **бэкапа нет**
- GitHub Environment `production` — деплой из `main` с ручным approval (см. HIGH #19)

**Единая точка отказа принята сознательно.** Горизонтальное масштабирование
(вторая VM + балансировщик, либо managed instance group) запланировано за
1-2 месяца до старта проекта, чтобы не увеличивать стоимость сервера на
этапе подготовки. Это решение, а не упущение — не удаляйте этот раздел
без обновления даты/статуса.

## Что осталось на совести оператора (бесплатно, но вручную)

1. **Yandex Cloud → Compute → эта VM → настройки** — проверить, что включён
   автоматический перезапуск ВМ при сбое хоста ("Restart policy" /
   аналог). Обычные (не preemptible) VM в Yandex Cloud по умолчанию
   переживают live migration при обслуживании хоста — preemptible/spot
   инстансы этой защиты не имеют. Убедитесь, что прод — НЕ preemptible.
2. **Бэкап `/home/yc-user/uploads`** — не автоматизирован (Object Storage
   стоит денег, хоть и немного — сознательно не подключали без вашего
   ОК). Пока — вручную, периодически:
   ```bash
   ssh yc-user@<prod-ip> "tar czf - -C /home/yc-user uploads" > uploads-backup-$(date +%F).tar.gz
   ```
   Скажите, если готовы выделить бюджет на Object Storage — подключим
   автоматический `rsync`/lifecycle-политику в отдельной задаче.

## Что делать при алерте "🔴 Prod down"

1. Проверить issue — там будет ссылка на прогон `uptime-monitor.yml` и
   время первого обнаружения.
2. SSH на прод-VM, проверить:
   ```bash
   sudo systemctl status docker nginx
   docker ps -a --filter name=baltcircle
   docker logs --tail 200 baltcircle-mvp
   ```
3. Если контейнер не поднимается — `cd` в директорию проекта,
   `docker compose up -d`.
4. Если VM не отвечает по SSH вообще — перезагрузить/пересоздать через
   консоль Yandex Cloud. Docker и nginx поднимутся сами (см. таблицу выше).
5. После восстановления `uptime-monitor.yml` сам закроет issue при
   следующем прогоне (максимум через 5 минут) — закрывать вручную не
   обязательно, но можно оставить комментарий с причиной инцидента для
   истории.

## Когда бюджет появится (план на будущее, не делать сейчас)

- Вторая VM + Yandex Network Load Balancer перед nginx — реальный failover
  при падении хоста.
- Отдельное staging-окружение (тот же стек, меньшая VM) — тестировать
  деплои перед прод без риска для реальных пользователей.
- Managed Instance Group вместо ручной VM — авто-восстановление и
  горизонтальное масштабирование "из коробки".

Ориентир по времени — начать за 1-2 месяца до запуска проекта (решение
пользователя от 2026-08-18).
